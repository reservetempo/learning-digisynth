About this site

This is the companion to a real, in-progress project: a standalone digital synthesizer written in C++ and JUCE, for a dedicated instrument built out of a tablet and a custom knob controller. That project is driven by a 13-phase plan of about 130 steps. The plan is written to be executed, not read, and it shows. This site is the readable half.

How the two fit together

The build lives in a folder called digi-synth0001. Its PLAN.md is the checklist — one line per step, a Verify command, and a tick when it is done. Steps are small on purpose: one unit of code, one test file, one green test run, at most about 400 new lines.

This site groups roughly three of those steps into one lesson, chosen so each lesson is one idea rather than one commit. The grouping ignores step numbering where step numbering would split an idea in half. Every lesson names the exact steps it shadows, so you can always go and read the original.

Built, or planned?

The instrument is not finished, and lessons are written ahead of it. Each lesson carries a badge:

Built  — the code exists. Every snippet on that page is quoted from the real file, with its path in the caption. What you read is what runs.

Planned  — the step has not been implemented yet. The design is settled and the lesson describes it faithfully, but the snippets are illustrative and say so in their caption. Expect the details to shift when the code is actually written; the ideas will not.

How each lesson is laid out

Every page follows the same ten blocks, so you always know where to look:

  1. In one sentence — what gets built, in plain words.
  2. Why it exists — the problem that forced it, before any solution.
  3. The walkthrough — the explanation proper, one new term at a time.
  4. Vocabulary — the words this lesson introduces, defined in a table.
  5. A diagram, where a picture genuinely helps.
  6. The code — two to four short snippets, each explained after it.
  7. The architecture idea — one transferable design lesson, named.
  8. The C++ or JUCE note — one language concept, explained properly.
  9. Go deeper — a few outside links worth the time.
  10. Check yourself — three questions with the answers hidden.

Words with a dotted underline link to the glossary. Every term is introduced once, in the lesson that first needs it, and linked from everywhere else.

Two words that mean two things

Synthesizer vocabulary is full of collisions, and one in particular will trip you up. Voice normally means "one sounding note" — a 16-voice synth plays 16 notes at once. In this project a voice is one of the six complete, independent synthesizers, each of which is itself polyphonic. This site says voice for the big one and note for the small one, everywhere, including where the source code does not.

Sample is the other one: it means both "one measurement of a waveform" and "a recording you can play back". Where it matters, this site says frame for the first and sample only for the second.

Reading order

Front to back works, and the parts are ordered so that nothing depends on something later. But the lessons are self-contained enough to jump around. Three reasonable routes:

  • You want to understand synthesizers. a1, then Parts G, H, I, J, K — the sound-making half. Skip Part C entirely.
  • You want to learn C++ and software architecture. a2, Part B, Part C, then d1, i1, i2 — the parts where the engineering ideas live.
  • You want to follow the build. Front to back, and stop where the Built badges stop.

Where the code lives

Snippets cite paths inside the synth project, like src/core/PolyFloat_avx2.h. The layout is: 

digi-synth0001/
  PLAN.md            the checklist: every step, and a tick when done
  CLAUDE.md          the working rules that bind every step
  docs/
    ARCHITECTURE.md  the design: threads, block cycle, parameters, layout
    CONVENTIONS.md   naming, file layout, include order
    steps/<id>.md    a note for each step that discovered something
  src/
    core/            the primitives: SIMD types, denormals, queues, thread pool
    params/          the parameter table and everything derived from it
    engine/          audio I/O, the synth engine, voices, note allocation
    dsp/             oscillators, wavetables, filters, modulators
      fx/            the twelve effect types and the chain that holds them
    mod/             the modulation matrix
    seq/             transport and the Euclidean sequencer
    ui/              theme, layout, encoders, displays
      pages/         the seven per-voice pages and the four sequencer pages
  tests/             one Catch2 suite per unit, mirroring src/

The docs/steps/ notes are the most interesting files in the whole project. Each one records something that went wrong or surprised someone — and those notes are where a lot of this site's content comes from.
